# DeepFilter 音声フィルターツール

DeepFilterNet3の公式ONNXモデルを公式Rust CLIで実行する、日本語の音声ノイズ除去ツールです。

2つの入り口があります。

| | 対象 | 用途 | 状態 |
|---|---|---|---|
| **DeepFilterTool.exe** | Windows | GUIで操作する | 実エンジンで検証済み |
| **deepfilter-tool** (`cli/`) | Windows / Linux / macOS | コマンドラインで処理する | Linuxで実エンジン検証済み |

どちらも同じ処理を行います。音声処理はすべてローカルで、通信は公式ファイルの取得時のみです。

開発・ビルド・テストの手順、環境変数の一覧、困ったときの対処は [docs/CONTRIBUTING.md](docs/CONTRIBUTING.md) にまとめています。

## 共通の仕様

- 入力は48 kHz、モノラルまたはステレオのWAV。PCM 16bit / IEEE Float 32bit対応。
- 最大ノイズ抑制を1〜100 dBで調整。100 dBは実質制限なし。ポストフィルターで除去を強められます。
- 出力は再生互換性のため48 kHz PCM 16bit。元のファイルは変更しません。
- 末尾に無音を追加して遅延補正後に元のフレーム数へ整えるため、入出力の長さは一致します。
- MP3、動画、マイクのリアルタイム処理は対象外です。大容量ファイルはメモリ使用量が増えます。

## Windows GUI版

`DeepFilterTool.exe` をダブルクリックして起動します。

1. WAVを選択し、必要なら抑制上限とポストフィルターを調整。
2. 「ノイズを除去」を押す。
3. 元音声と処理後を再生して確認し、「名前を付けて保存」。

.NET Framework（Windows標準）で動作します。再ビルドは `Build.cmd`（Windows標準のC#コンパイラを直接使用、外部パッケージなし）。既存EXEがある場合は上書きを拒否します。

### テスト

| スクリプト | 生成物 | 内容 |
|---|---|---|
| `Build-Tests.cmd` | `Tests.exe` | `WaveData` の単体テスト60件。エンジン不要、数十ミリ秒で終わる |
| `Build-Verify.cmd` | `Verify.exe` | 実エンジンとGUIを通す統合テスト |

```
Tests.exe            すべて実行
Tests.exe Read_      名前で絞り込んで実行
```

.NET SDK・NuGet が使えない環境（Windows同梱の `csc.exe` のみ）のため、xUnit相当の仕組みは `Tests.cs` 内に最小限だけ自作しています。`[Fact]` / `[Theory]` + `[InlineData]`、テストごとに新しいインスタンスを作る点、Arrange-Act-Assert、`メソッド_期待する結果_条件` の命名、テストデータビルダーはxUnitの流儀に合わせています。外部パッケージは使いません。

## クロスプラットフォームCLI版

`cli/` にあるRust実装です。**外部クレートを一切使わず標準ライブラリのみ**で書かれているため、cargoがあればオフラインでビルドできます。

### ビルド

```bash
cd cli && ./build.sh
```

Windowsでは `cli\build.cmd`（Rust の MSVC ツールチェーンが必要）。

Linuxではmuslターゲットが入っていれば `build.sh` が自動的にそれを選び、**システムのCコンパイラなしで完全静的バイナリ**を作ります。gccやbuild-essentialを入れられない環境向けです。

```bash
rustup target add x86_64-unknown-linux-musl   # 事前に一度だけ
```

### 公式エンジンの導入

```bash
./target/x86_64-unknown-linux-musl/release/deepfilter-tool setup
```

実行中の環境に合う公式バイナリとモデルを `runtime/` に取得し、**サイズとSHA-256を照合してから配置**します。照合に失敗したファイルは破棄されます。すでに正しいファイルがあれば再取得しません。

`--platform <キー>` で他環境向けのファイルも取得できます（`windows-x86_64` / `linux-x86_64` / `linux-aarch64` / `macos-x86_64` / `macos-aarch64`）。macOSではGatekeeperの検疫属性を自動で外します。

導入状態は `deepfilter-tool check` で確認できます。

### 使い方

```bash
deepfilter-tool 録音.wav                          # 録音_clean.wav を作る
deepfilter-tool 録音.wav -o きれい.wav -a 60 --pf  # 出力先・抑制上限・強めの除去を指定
deepfilter-tool --help                            # 全オプション
```

| オプション | 意味 |
|---|---|
| `-o, --output <ファイル>` | 出力先。既定は 入力名`_clean.wav` |
| `-a, --attenuation <1-100>` | 最大ノイズ抑制 dB。既定は100 |
| `--pf` | 強めの除去（ポストフィルター） |
| `--force` | 出力先が既にある場合に上書き |
| `--keep-session` | 作業フォルダーを残す |
| `--engine` / `--model` | エンジン・モデルの場所を指定 |
| `-q, --quiet` | 処理中のメッセージを出さない |
| `--debug` | 詳細なログを標準エラーへ出す |

サブコマンドは `setup` / `check` / `manifest`。`-h` / `--help` / `help`、および引数なしの実行で、全オプションと使用例を含む使い方を表示します。`-V` / `--version` で版を表示します。

`runtime/` と `sessions/` の場所は、実行ファイルの位置（4階層上まで）から自動で探します。環境変数 `DEEPFILTER_HOME` で明示できます。

**カレントディレクトリは意図的に探索対象から外しています。** ここを含めると、細工した `runtime/deep-filter` を置いたフォルダーに移動して実行するだけで任意のプログラムが起動してしまうためです。信頼できない場所で作業する場合も安全に使えます。

### 詳細ログ

`--debug` を付けると、処理の流れを標準エラーへ出します。環境変数 `DEEPFILTER_DEBUG=1` でも有効になります。標準出力には出さないので、`-q` と併用しても、出力をパイプでつないでも混ざりません。

各行に処理開始からの経過時間が付き、解決したエンジンとモデルの場所、入力WAVの形式・長さ、パディング量、公式エンジンに渡した引数そのもの、エンジンの終了状態と所要時間、エンジン自身のログ（`-v` を連動して渡します）、切り詰め結果までを追えます。調査できるよう、作業フォルダーも自動的に残します。

```
[debug   0.001s] 入力WAV : 48001 フレーム / 1 ch / 48000 Hz / PCM (16 bit) / 96002 バイト
[debug   0.001s] パディング: 48001 -> 53280 フレーム（ホップ 480 に切り上げ + 末尾 4800）
[debug   0.001s] 実行     : …/deep-filter -m …/DeepFilterNet3_onnx.tar.gz -D -a 80 --pf -v -o … …
[debug   0.302s] エンジン終了: exit status: 0 / 0.301 秒
[debug   0.302s] エンジン出力: 51840 フレーム / PCM (16 bit)
[debug   0.302s] 48001 フレームへ切り詰め: …/clean.wav
```

`setup` や `check` でも使えます。`setup --debug` では取得URL、配置先、SHA-256の期待値と実測値が出ます。

### 効果の実測値

実際の録音（3.94秒、48 kHz モノラル、ノイズなしの音声に雑音を重ねたもの）で測定した結果です。

| 指標 | 処理前 | 処理後 | 差 |
|---|---|---|---|
| SNR | 20.00 dB | 22.52 dB | **+2.52 dB** |
| 残留ノイズのエネルギー | 0 dB（基準） | -2.52 dB | **44% 減** |
| 無音区間のノイズ床（RMS） | 253.6 | 144.3 | **-4.90 dB** |
| 声の区間のエネルギー | 基準 | -0.23 dB | ほぼ保持 |
| 時間のずれ | — | 0 サンプル | ずれなし |

設定を変えた場合（同じ音源）:

| 設定 | 処理後 SNR | 改善 | 無音区間 RMS |
|---|---|---|---|
| 既定（`-a 100`） | 22.52 dB | +2.52 dB | 144.3 |
| `--pf` | 22.54 dB | +2.54 dB | 142.9 |
| `-a 60` | 22.52 dB | +2.52 dB | 144.4 |
| `-a 60 --pf` | 22.54 dB | +2.54 dB | 143.0 |
| `-a 30` | 22.51 dB | +2.51 dB | 146.8 |
| `-a 20 --pf` | 22.51 dB | +2.51 dB | 151.0 |

読み取れること:

- **無音区間のノイズ床が約 -4.9 dB（振幅で 57%）下がり**、声の区間のエネルギーは -0.23 dB とほぼ変わりません。声を削らずに雑音だけを落とせています。
- 全体の SNR 改善が +2.5 dB に留まるのは、元の音源が既に 20 dB と比較的きれいで、残差に「取り切れなかった雑音」だけでなく「モデルによる声のわずかな変化」も含まれるためです。より雑音の多い音源ほど改善幅は大きくなります。
- **設定による差はごくわずか**です。`-a` は抑制の上限を決める値で、この音源では上限に達していないため効きません。雑音が大きい音源で差が出ます。`--pf` はわずかに強く効きます。
- 処理の前後で**時間が 1 サンプルもずれません**（遅延補正が正しく働いています）。

この測定は `cli/tests/noise_reduction.rs` で自動化しています。手元の音源で確かめるには、ノイズのない音声と、それに雑音を重ねた音声（**同じ長さ・同じ時間位置**）を用意し、`samples/clean.wav` と `samples/noisy.wav` に置くか、環境変数 `DEEPFILTER_CLEAN` / `DEEPFILTER_NOISY` で指定してください。音声ファイル自体はリポジトリに含めません。

### ファイル名の文字コード

日本語（全角）のファイル名・フォルダー名をそのまま扱えます。濁点・半濁点は合成済み（NFC）でも結合文字（NFD、macOSの正規化形）でも、半角カタカナ、絵文字、空白や記号を含む名前でも同様です。

内部ではパスを文字列に変換せず、OSのファイル名表現のまま受け渡します（`OsString` / `OsStr`）。Windowsでは UTF-16、Linux/macOSではバイト列として扱うため、**UTF-8ではないファイル名**（古い環境から持ち込んだShift_JIS名など）でもエラーにならず処理できます。公式エンジンには常に `input.wav` という固定名で渡すので、エンジン側の文字コードの扱いに影響されません。

なお、UTF-8でないファイル名が実際に存在しうるのはLinuxなど、ファイル名を任意のバイト列として扱うファイルシステムだけです。macOSのAPFSは妥当なUTF-8しか受け付けず（`Illegal byte sequence` で作成そのものが失敗）、WindowsのファイルシステムはUTF-16のため、これらの環境ではこの状況が発生しません。該当のテストは、ファイルシステムが受け付けない場合に理由を示して検査を飛ばします。

引数はシェルを介さず個別の値として子プロセスへ渡すため、空白・記号・引用符の有無で挙動が変わりません。パスの書き方（絶対・相対・`./`・`..`）が違っても同じファイルとして扱い、入力と同じファイルを別の書き方で出力先に指定した場合も上書きせずに断ります。

**どのOSでも持ち運べる出力名だけを受け付けます。** Windowsの予約デバイス名（`NUL`、`CON`、`COM1` など。拡張子を付けても同じ扱いです）、末尾の空白や `.`、`< > : " | ? *` を含む名前は、LinuxやmacOSで実行した場合も断ります。予約名に書くと内容がどこにも残らないまま成功したように見え、末尾の空白や点はWindowsが黙って削って別名のファイルになるためです。日本語・全角記号・絵文字はそのまま通ります。

**PowerShell での注意（Windows PowerShell 5.1）:** 画面に直接表示する分には日本語が正しく出ますが、出力をパイプやリダイレクトで受けると、PowerShell 5.1 は既定でOSのコードページ（日本語環境では932）として解釈するため文字化けします。次のいずれかで解消します。

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8   # 5.1 で一時的に
```

PowerShell 7 以降は既定が UTF-8 のため、この対処は不要です。

## 供給網（サプライチェーン）対策

このプロジェクトには **npm も NuGet も存在せず、Rust の外部クレートもゼロ**です（`cli/Cargo.lock` のパッケージ数は1＝自分自身のみ）。したがってパッケージレジストリ経由の攻撃面がありません。実際の供給網は「公式配布物の取得」と「CIで使うGitHub Actions」の2つで、それぞれに対策しています。

**1. 公式配布物（DeepFilterNetのエンジンとモデル）**

- 版・取得元URL・バイト数・SHA-256を `cli/src/assets.rs` に固定。`runtime/manifest.json` はここから生成されます。
- 取得前にURLのスキームを検査し、**HTTPS以外は取得しません**。curl / wget にもプロトコルとTLSの下限を明示します。
- **配置前に必ずサイズとSHA-256を照合**し、一致しないものは破棄して `runtime/` に置きません。差し替えられた配布物を掴んでも実行されません。
- 取得ツールは絶対パスに解決してから起動し、同名プログラムの取り違えを防ぎます。

**2. GitHub Actions**

- 使用するアクションは**すべて40桁のコミットSHAで固定**します。タグは書き換え可能なため使いません。CIの `supply-chain` ジョブがタグ参照を見つけると失敗します。
- 第三者製アクションは使っていません（`actions/checkout` のみ）。ツールチェーンはランナー同梱の `rustup` を直接呼びます。
- CIで取得する `cargo-llvm-cov` はバージョンとSHA-256を固定し、照合してから使います。
- ワークフローの既定権限は `contents: read`、チェックアウトは `persist-credentials: false`。

**3. 依存ゼロの維持**

CIの `supply-chain` ジョブが、`Cargo.lock` のパッケージ数が1でなくなった時点、または `[dependencies]` に項目が増えた時点で失敗します。うっかり依存が入ることを仕組みで防ぎます。

> ご提案いただいた [setup-takumi-guard-npm](https://github.com/flatt-security/setup-takumi-guard-npm) は npm / pnpm / Yarn 専用で、公式に「Rust/Cargo、.NET/NuGet、任意のファイルダウンロードは対象外」と明記されています。本リポジトリには npm パッケージが1つもないため導入しても保護対象がなく、代わりに上記の対策を実装しました。将来 Node.js を使う部分を追加する場合は、そのワークフローに導入する価値があります。

## セキュリティ

- **エンジンの探索にカレントディレクトリを使いません。** 実行ファイルの位置と `DEEPFILTER_HOME` のみです。
- **取得は HTTPS のみ。** 取得前にURLのスキームを検査し、curl / wget にもプロトコルとTLSの下限を明示します。取得ツールは絶対パスに解決してから起動します。
- **配置前に必ずサイズと SHA-256 を照合します。** 一致しないものは破棄し、`runtime/` には置きません。
- 外部クレートに依存しないため、第三者パッケージ経由の供給網リスクがありません（`Cargo.lock` のパッケージ数は1）。
- `unsafe` ブロックはありません。本番の処理経路に `unwrap` / `expect` / `panic!` はありません。
- 認証情報・トークンの類は扱いません。

既知の残存リスク:

- `runtime/` に書き込める者は、照合の直後から配置までのごく短い隙にファイルを差し替えうる（TOCTOU）。ただしその権限があれば配置後に直接置き換えることもできるため、実質的な追加リスクはありません。`runtime/` の書き込み権限は利用者本人に限ってください。
- `--debug` は絶対パスを標準エラーに出します。ログを共有する場合はご注意ください。

## プライバシー

処理ファイルとエンジンログは `sessions/日時-ID` に保存されます。入力の作業用コピーも含まれるため、プライベートな音声を扱う場合はこのフォルダーも同様に管理してください。GUI版は自動削除しません。CLI版は成功時に既定で削除します。
